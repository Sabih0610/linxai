# QA and security review — 13 November 2026

A QA pass over the whole product: an independent read-only code review (security and
best practice), the AI evaluations against the real local model, the offline suites on
Windows and Linux, the desktop under Qt, the network lab regression, and a red-team run on
the real kernel (section 4, run by the owner at the VM console).

## 3. Known limits and gaps (not fixed here)

* **Blocking is outbound only and pre-approved.** The kernel response blocks the owner
  account's TCP connections to an exact IPv4 address and port that root listed in
  `/etc/linxai/response.json` (maximum 32). It cannot block an inbound port an attacker came
  in through, a newly seen attacker address, UDP or IPv6.
* **IPv6 and v4-mapped connections** are neither detected nor blocked (probes and the BPF
  LSM program handle IPv4 only).
* **Detection rules are name and list based.** Interpreter reverse shells (python, perl),
  renamed tools and C2 on ordinary ports (443) are not detected; relative paths are judged
  as typed. The red-team run in section 4 measures this on the real kernel.
* **The monitor and its incident store run under the watched account**, so a compromised
  owner account can stop it or edit incidents (the root sensor evidence survives).
* **Event floods** can make the sensor drop events (health turns degraded, but no incident).
* **Development environments exist for Python and Node only.** Docker, Go and C++
  environment recipes are not implemented.
* `remote.operation` is labelled unprivileged in the preview although it runs `sudo -n`
  on the target.
* The legacy `linxai-core` and `linxai-ebpf` services must be disabled on the VM by an
  administrator (`sudo systemctl disable --now linxai-core linxai-ebpf`).

## 4. Red-team run on the real kernel (VM, 13 November 2026)

Target: Ubuntu 24.04.4, kernel 6.8.0-147, BPF LSM active; trusted bundle rebuilt from
commit a14a75d (manifest-verified) and deployed with the sensor, broker and policy daemon;
monitor as the ordinary owner. The owner typed the administrator password at the console;
everything else was driven remotely. Evidence: `evidence/qa-2026-11-13/`.

**Kernel qualification** (`qa-gate-e-qualify.json`): passed, `actual_kernel_probe`; cases
deny, uid/port/address/UDP near-matches, revoke, expiry.

**Detection** (`qa-redteam-detect.json`, `scripts/redteam_detect.py`): 7 of 14 attacker
techniques detected, every expected one, 0.11–0.66 s; 0 false alarms on curl, python
connect and ls.

| Technique | Result |
| --- | --- |
| bash `/dev/tcp` reverse shell | detected 0.56 s (`shell_network_connection`) |
| netcat reverse shell | detected 0.53 s |
| connection to backdoor port 4444 | detected 0.11 s (`unusual_connection_attempt`) |
| tool executed as `nmap` | detected 0.66 s (`attack_tool_execution`) |
| payload executed from `/tmp` | detected 0.62 s (`temporary_executable_attempt`) |
| read of `/etc/shadow` | detected 0.18 s (`sensitive_file_attempt`) |
| read of `/etc/gshadow` | detected 0.36 s (new with fix 5) |
| python / perl reverse shell on an ordinary port | **not detected** |
| netcat copied as `kworker`; renamed scanner | **not detected** |
| reverse shell over IPv6 | **not detected** |
| opening `~/.ssh/authorized_keys` for writing | **not detected** |
| inbound bind shell | **not detected** |

**Detect → block → retry** (`qa-redteam-block.json`, `scripts/redteam_block.py`): 8/8.
Reverse shell to 127.0.0.1:4444 → incident in 0.55 s → block built from the evidence (the
model timed out and was not needed: fix 12) → polkit approval by the owner → BPF LSM
policy installed and verified by the broker → attacker retries with bash and python both
refused with EPERM → adjacent port 4443 still connects → the policy expired by itself in
the kernel and the target was reachable again. The 87 s from attack to block includes the
owner typing the password.

Run 1 (`qa-redteam-block-run1-harness-bug.json`) reported the bash retry as connected:
a test-harness bug (a failed `exec 3<>/dev/tcp/...` does not stop `bash -c`, which still
exits 0). The check now reads bash's own error; run 2 shows the bash retry refused with
EPERM. Two lab issues were also found: a leftover June nginx config listens on 4444 on the
VM (the scripts reuse an existing listener), and the monitor must be started through its
`main()` (the module has no `__main__`).
